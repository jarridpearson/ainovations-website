# Test matrix — dedicated add-on subscription architecture

No Stripe/Supabase test harness exists in this repo (no `deno.json`, no existing
`*_test.ts` files), so full integration tests aren't feasible to stand up as part
of this diff. This matrix documents the scenarios that must be manually verified
against a Stripe test-mode account before deploying, plus what to check in the
database for each. `replaceItemDefinition` (the one piece of new pure logic) has
an executable Deno unit test alongside this file.

Legend: BASE = `stripe_subscription_id` (plan + seats). ADDON = `stripe_addon_subscription_id`
(AI credit add-ons only).

| # | Scenario | Trigger | Expected result | Verify |
|---|----------|---------|------------------|--------|
| 1 | Base subscription created (signup) | `create-organization-checkout` → `checkout.session.completed` | `organizations.stripe_subscription_id` set. `stripe_addon_subscription_id` untouched (still null). Addon credit ledgers **not** synced/zeroed. | `organizations` row; `ai_credit_ledger` unaffected |
| 2 | Base subscription seat increase | `manage-organization-billing` `update_seats` (immediate) → Stripe seat-add checkout → `complete-organization-seat-checkout` → `customer.subscription.updated` | BASE items change. ADDON subscription/items untouched. Addon credit ledgers **not** resynced by this event. | `organizations.paid_seat_count`; `ai_credit_ledger.recurring_addon_allocation` unchanged |
| 3 | Base subscription seat decrease (scheduled) | `update_seats` (renewal path) | Stripe subscription schedule created on BASE only. ADDON has no schedule created. | Stripe dashboard: schedule attached to BASE subscription id, not ADDON id |
| 4 | Base plan change (starter ↔ pro) | `schedule_plan` | Same as #3 — schedule on BASE only | same |
| 5 | Base subscription renewal invoice paid | `invoice.paid` for BASE subscription | `handleInvoiceEvent` updates `subscription_status`. **Addon sync RPCs are NOT called** (gated on `subscription_kind === "ai_addons"`, and this invoice's subscription has no such metadata). | Before fix: `ai_credit_ledger.recurring_addon_allocation` would drop to 0 here. After fix: unchanged. |
| 6 | Base subscription cancelled | `cancel_subscription` action → `customer.subscription.updated` (`cancel_at_period_end: true`) → later `customer.subscription.deleted` | BASE `stripe_cancel_at_period_end` set, then `subscription_status` → `canceled` at period end. ADDON subscription and its credits are **not** affected by base cancellation. | `organizations.stripe_addon_subscription_id` still set if an add-on subscription independently exists |
| 7 | Add-on purchase (no existing add-on subscription) | `create-organization-addon-checkout` → `checkout.session.completed` (`subscription_kind: ai_addons`) | `organizations.stripe_addon_subscription_id` set. `synchronizeSubscription`'s `ai_addons` branch runs, calls both sync RPCs with the ADDON subscription's items. Ledger allocation reflects purchased credits. | `organizations.stripe_addon_subscription_id`; `ai_credit_ledger.recurring_addon_allocation` for both `app` and `portal` pools |
| 8 | Add-on purchase attempted while one already exists | `create-organization-addon-checkout` | Rejected with 409 "already has an AI add-on subscription" (pre-existing guard, unchanged) | HTTP 409 |
| 9 | Add-on quantity increase (upgrade) via `manage-organization-billing` | `update_addon`, `requestedCredits > currentCredits`, `addonSubscription` exists | Stripe item updated on **ADDON** subscription id (not BASE). Proration invoice created. On payment, `synchronizeOrganizationCreditAddons` called with the refetched ADDON subscription. | Stripe: item change on ADDON id; ledger reflects new allocation after invoice paid |
| 10 | Add-on quantity increase attempted with no add-on subscription yet | `update_addon` / `preview_change` (`changeType: "addon"`), `!addonSubscription` | 409 `{ requiresAddonCheckout: true }` — caller must use `create-organization-addon-checkout` | HTTP 409, no Stripe call made against BASE |
| 11 | Add-on renewal (recurring invoice paid on ADDON subscription) | `invoice.paid` where `invoice`'s subscription has `metadata.subscription_kind === "ai_addons"` | `handleInvoiceEvent` retrieves that subscription, confirms `ai_addons` kind, calls `synchronizeOrganizationCreditAddons` with it. Ledger allocation reconfirmed for the new period. | `ai_credit_ledger.recurring_addon_allocation` matches ADDON subscription's current items |
| 12 | Add-on decrease, other pool still active (e.g. cancel portal, keep app) | `update_addon`, `requestedCredits < currentCredits`, resulting `futureItems.length > 0` | `scheduleItemsAtRenewal` runs on the ADDON subscription with the remaining item(s). No cancellation. | Stripe schedule phase on ADDON id with 1 item; `organization_billing_change_requests` row `change_status: scheduled` |
| 13 | Add-on cancellation (last remaining pool reduced to 0) | `update_addon`, `requestedCredits === 0`, resulting `futureItems.length === 0` | **New branch**: any existing schedule on ADDON is released, then `stripe.subscriptions.update(addonSubscription.id, { cancel_at_period_end: true })`. No attempt to schedule a zero-item phase (which Stripe would reject). | Stripe: ADDON subscription `cancel_at_period_end: true`; `organization_billing_change_requests.metadata.addon_subscription_canceled: true` |
| 14 | Add-on subscription actually ends at period end | `customer.subscription.deleted` for the ADDON subscription (`subscription.status === "canceled"`) | **New behavior**: `organizations.stripe_addon_subscription_id` is cleared to `null` (previously stayed set forever, permanently blocking re-purchase via `create-organization-addon-checkout`'s existing-subscription guard). `synchronizeOrganizationCreditAddons` still runs once more with `status: "canceled"`, zeroing both pool allocations. | `organizations.stripe_addon_subscription_id IS NULL`; `ai_credit_ledger.recurring_addon_allocation = 0` for both pools; org can immediately re-purchase |
| 15 | `get_state` polling / dashboard load, no add-on subscription | `manage-organization-billing` `get_state` | No RPC calls made (nothing to sync). Response includes `hasAddonSubscription: false`, `currentPortalAddonCredits: 0`, `currentAppAddonCredits: 0`. | Response body only — no Stripe/DB writes |
| 16 | `get_state` polling / dashboard load, add-on subscription active | `get_state` | Sync RPCs called with the ADDON subscription (not BASE). Response includes `hasAddonSubscription: true` and real credit counts. | `ai_credit_ledger` values match what's returned |

## Regression checks specific to this diff

- Confirm `create-organization-checkout` still succeeds for a brand-new org signup with the two addon params removed from its request/response contract (no caller currently sends them — verified against `everward-portal/src/components/OrganizationSignup.tsx`, which calls `create-organization-signup`, which forwards to this function but currently always sends empty strings for both keys).
- Confirm `deno check` (or an equivalent Deno-aware type check — not available in this environment) passes for all three edited functions once actually run in a Deno context; a Node/tsc syntax pass with Deno globals stubbed out found zero syntax errors, but full Stripe/Deno type coverage requires the real Deno toolchain.
